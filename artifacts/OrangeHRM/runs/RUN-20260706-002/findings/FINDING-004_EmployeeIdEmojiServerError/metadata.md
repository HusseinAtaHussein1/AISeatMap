# FINDING-004

- **Finding ID:** FINDING-004
- **Title:** Employee Id uniqueness-check endpoint returns HTTP 500 for emoji input
- **Category:** Bug
- **Severity:** Medium
- **Severity Reason:** Matches Medium ("validation issues / business rule inconsistencies") — an input-validation code path throws an unhandled server error rather than returning a graceful validation result. Does not reach High/Critical: the Add Employee form itself remains usable and the failure does not block the core workflow (a user simply cannot use emoji in this field, which is a reasonable restriction to have — the bug is the *ungraceful* failure mode, not the restriction itself).
- **Confidence Score:** 98%
- **Status:** Confirmed
- **Business Risk:** Low direct business impact (emoji is not a realistic Employee Id value), but this is the **second independent confirmation** (alongside `FINDING-001` in Login) of the same systemic input-handling gap, which raises the likelihood that other text fields across the application share the same latent defect.
- **Technical Risk:** The live-validation endpoint `GET /api/v2/core/validation/unique` (triggered on-blur while filling the Add Employee form, before any Save) throws an unhandled server-side exception for any value containing a 4-byte-UTF8 (emoji/supplementary-plane) character, regardless of the value's overall length. The response is a generic `{"error":{"status":"500","message":"Unexpected Error Occurred"}}` — no stack trace or internal detail is leaked, which is a positive security property even though the underlying defect remains.
- **Module:** PIM — Employee Management (Add Employee form)
- **Workflow:** Add Employee — Employee Id field validation (PRD FR-9)
- **Description:** While filling the Add Employee form's Employee Id field, the application performs an asynchronous uniqueness check against the entered value. If that value contains an emoji character — even a single one, with nothing else in the field — the check fails with an HTTP `500` instead of returning a normal uniqueness result, and the frontend surfaces its own additional JS console errors on top of the network failure.
- **Expected Behavior:** Not explicitly defined in the Project Context/PRD for this input class (same gap as `FINDING-001`). The reasonable baseline is the field's own correct behavior for every other tested input (numeric, long numeric, etc.), all of which return a normal `200` uniqueness result.
- **Actual Behavior:** Isolated via a boundary sweep of the Employee Id field's live-validation endpoint:

  | Value | Result |
  |---|---|
  | `0390` (pre-filled default) | `200 OK` |
  | `1234567890123456789012345678901234567890` (40 digits, no emoji) | `200 OK` (both attempts) |
  | `😀EMOJI-TEST-` + 40 digits (53 chars, with emoji) | **`500`** (both attempts) |
  | `😀` (1 character, emoji only) | **`500`** |

  The failure is caused purely by the presence of an emoji character, independent of overall string length — confirmed by the 40-digit-only value succeeding while the single-emoji-only value fails.
- **Steps to Reproduce:** 1) Log in, navigate to PIM > Add Employee. 2) Enter any emoji character into the Employee Id field (leave Full Name blank so the form can never actually be saved). 3) Click Save (or blur the field, which triggers the same async check) — do not fill Full Name, so no employee is ever persisted. 4) Observe the `500` response on `GET .../api/v2/core/validation/unique?...` in the network log and the resulting console errors.
- **Investigation/Recovery Result:** Failure category: not a clean match for any Investigation & Recovery Engine category (not Navigation/Timeout/Validation-failure-in-the-deterministic-sense/Network-failure/Unexpected-UI-rendering — the request itself completes, just with a `500` status). Default: "No retry." Validated by reproducing twice with the original long+emoji value and confirming the isolated single-emoji case separately — 3 total reproductions of the same underlying condition.
- **Investigation Notes:** This candidate was found while investigating a different boundary (long input) on the same field — the emoji was included in that first test string incidentally (as part of a combined "long + unusual characters" probe) and turned out to be the actual cause once isolated. This is a direct structural match to `FINDING-001` (Login Username field, same emoji/4-byte-UTF8 trigger, same generic "Unexpected error"/"Unexpected Error Occurred" message pattern) — strongly suggesting a **shared root cause across the codebase** (e.g., a common database-access layer or shared validation utility with the same encoding limitation), rather than two independent, unrelated bugs. This is recorded as an explicit cross-reference rather than being merged into a single Finding, since they occur in different modules/endpoints and Duplicate Detection (§5.9) requires the same underlying condition in the same module/workflow to merge — these are the same *class* of defect, not literally the same occurrence.
- **Root Cause Hypothesis:** *Possible Root Cause:* the same database column-encoding limitation hypothesized in `FINDING-001` (`utf8` vs `utf8mb4`), here affecting the `employeeId` column's uniqueness-check query instead of the `username` lookup — consistent with both failures sharing the exact same generic error-message wording pattern ("Unexpected error occurred" / "Unexpected Error Occurred"), suggesting a shared exception-handling utility across both code paths. *Confidence:* 75% (higher than `FINDING-001`'s standalone hypothesis, strengthened by this second, independent confirmation in a different module). *Supporting Evidence:* identical failure signature (emoji-specific, length-independent, generic message) across two unrelated endpoints. *Unknowns:* whether this pattern holds for every text field across the application (not exhaustively tested this run — flagged as a Test Gap) or is coincidentally similar in just these two cases.
- **Occurrence Count:** 1 (3 reproductions of the same underlying condition; see also the related, structurally-similar `FINDING-001` in a different module, cross-referenced above rather than merged)
- **Evidence Links:** `failure.png` (form state after the single-emoji-only reproduction, with the `Required` validation for Full Name still visible, confirming no employee was ever created). Network response body for the `500` quoted inline above.
- **Recommendation:** Given this is the second independent confirmation of the same defect class (see `FINDING-001`), recommend escalating this as a single, cross-cutting investigation item for the development team — likely one shared root cause (e.g., a database encoding fix, or a shared input-sanitization step before any field reaches a lookup/uniqueness query) rather than two separate point fixes. Also recommend the Test Design Agent generate an explicit "emoji in any text-input field" regression test category, given the demonstrated cross-module pattern.
