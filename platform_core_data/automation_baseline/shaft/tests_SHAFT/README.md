## Credentials

The QA Super Admin credentials are held in `src/main/java/utilities/EnvironmentConfig.java`
(`USERNAME` / `PASSWORD`), so the suite runs from any terminal or IDE with no setup step. Keep them
in that one class — never inline a credential in a test or page class. To point the suite at a
different environment, change those two constants alongside `environment.properties`.

## Running the suite

```bash
mvn test                                    # whole-project regression — every promoted module
mvn test -DsuiteXmlFile=testng-branch.xml   # branch only (module-scoped, Stage 5A/5H reruns)
mvn test -DsuiteXmlFile=testng-agency.xml   # agency only (module-scoped, Stage 5A/5H reruns)
```

Plain `mvn test` compiles the project and runs `testng.xml` — now suite name
`NDCAdminPortalAutomationSuite` — via the Maven Surefire plugin. It declares every promoted module's
suites: Branch's `CreateBranchSuite` / `SearchBranchSuite` / `BranchActionsSuite` /
`UpdateBranchSuite`, and Agency's single `AgencyUpdateSuite` (added 2026-08-24). A module-scoped run
uses that module's own `testng-{module}.xml` instead — each file's ownership is recorded in
[`.baseline_ownership.json`](.baseline_ownership.json). Under SHAFT 7.4, Allure results are written
to **`allure-results/` at the project root** — not under `target/` — so view them with
`allure serve allure-results`.

`run-tests.bat` is the same `mvn test` with ReportPortal disabled. `generate_allure_report.bat`
serves an existing result set, but it is **machine-specific and regenerated by SHAFT on every
build** — it hardcodes the building machine's `JAVA_HOME` and `.m2` Allure CLI path, so a local
`mvn` run will rewrite it and show it as modified in `git status`. Prefer
`allure serve allure-results` directly, and do not commit the rewritten `.bat`. SHAFT also rewrites
`src/main/resources/properties/default/*.properties` the same way.

To compile only (no execution) — the check this project's own generation used for self-review:

```bash
mvn test-compile
```

## Target environment

`src/test/resources/environment.properties` — non-secret (base URL, paths only). Change this file,

## Test data

`src/test/resources/branch_baseline.properties` holds every value shared by more than one test:
the creation baseline, the environment's master data (Operating Country → Country, State, City,
Credential Name), and the two pre-existing STG records the read-only Search suite refers to.
Test-case-specific values — boundary inputs, the non-matching search code, per-case remarks — stay
in the test class that uses them.

Two consistency rules are enforced by comment in that file, not by code, so read them before
editing:

- `operatingCountry` and `country` are one mapping. TC-BR-004 asserts that selecting the first
  auto-fills the second.
- `targetAmount` must stay below `creditLimit`; the application rejects a target that is not.

`knownBranchCode` and `knownBranchName` are **independent fixtures, not a code/name pair** — they
name two different branches, used by two different test cases. Do not reconcile one to the other.

Approval-state labels (`Pending for approval`, `Approved`, `Rejected`) are defined once in
`ApprovalStatus.java` and read from there by both the tests and `AddBranch_Page`.

**Agency** test data lives separately: `src/test/java/utilities/AgencyFixture.java` builds the
class-scoped Agency fixture each test class needs, `AgencyDataFactory` (in `src/main/java/utilities/`)
generates unique field values, and `src/test/resources/testDataFiles/agency/` holds the fixed upload
fixtures (`agency-data.json` plus the `uploads/` PDFs and logo images used by
`AgencyDocumentsAndLogo_TC`).
