# FINDING-001 — Payment Option checkbox group contains ~25 non-payment-method entries

- **Finding ID:** FINDING-001
- **Title:** Payment Option checkbox group contains ~25 non-payment-method entries
- **Category:** Observation
- **Severity:** N/A
- **Severity Reason:** Category `Observation` is always N/A per the Severity Matrix — reclassified from `Bug` after human review (see Investigation Notes) established this is intended cross-module behavior, not a defect.
- **Confidence Score:** 95%
- **Evidence Category:** Direct Observation, corroborated by Human Observation (module-owner clarification, 2026-08-03)
- **Status:** Rejected
- **Business Risk:** A user creating or editing a Branch faces a Payment Option list mixed with ~25 unrelated, person-name-labeled checkboxes (and two single-letter "m"/"f" checkboxes), making the mandatory Payment Option selection confusing and error-prone, and raising doubt about whether the underlying data source is correctly scoped.
- **Technical Risk:** Suggests the Payment Option control is bound to the wrong lookup/data source (e.g. a Contacts/Staff/Faker-seeded table) rather than a dedicated Payment Method list — the same kind of cross-binding could affect other option lists built the same way.
- **Module:** branch
- **Workflow:** Admin → Branch → Create Branch → Branch Sales Configuration → Payment Option
- **Description:** The "Payment Option *" checkbox group on the Create Branch form renders the 5 expected payment methods (Cash, Wallet, Credit Card, BANQUE MISR, Fawry) immediately followed by roughly 25 additional, unlabeled-as-payment checkboxes whose labels are person first names (Isaiah, Filomena, Astrid, Olive, Dan, Rico, Collin, Bryant, Emilio, Tracy, Alma, Desmond, Enda, Hiram, Shannon, Quinton, Monserrate, Joey, Israel, Kasi, Joan) plus two single-letter checkboxes labeled "m" and "f".
- **Expected Behavior:** "The user may select Payment Options (multi-select checkboxes)." (PRD_UserStories.md US 5 §Branch Sales Configuration) — implies the checkbox set is limited to payment methods (Cash, Wallet, Credit Card, etc., per PRD.md PAY-03).
- **Actual Behavior:** The Payment Option checkbox group contains the 5 legitimate payment methods plus ~25 additional checkboxes with person-name/single-letter labels unrelated to payment methods.
- **Steps to Reproduce:** 1) Log in as Super Admin. 2) Navigate to Admin → Branch → Add branch (`/admin/branch/add`). 3) Scroll to the "Payment Option *" row in Branch Sales Configuration. 4) Observe the full checkbox list.
- **Investigation/Recovery Result:** Failure category "Unexpected UI rendering" (§5.7) — recovery behavior is "refresh the page once." Applied via two independent fresh navigations to `/admin/branch/add` in separate authenticated sessions (evidence: `before.png` from the first navigation, `failure.png` from a second, independent navigation after further probing). The anomaly persisted identically both times — outcome: persisted after recovery attempt.
- **Investigation Notes:** Probed as a Validation-adjacent candidate; the anomalous checkboxes were inspected visually (screenshot) rather than via DOM attribute dump, since the goal was confirming visible/selectable state, which a screenshot demonstrates directly. Did not attempt to select one of the anomalous checkboxes and submit, since the run's mutation authorization is scoped to Branch record actions (Create/Submit/Approve/Reject) and submitting with a deliberately corrupted selection risks creating a malformed real record — skipped per Environment Constraints, and noted here rather than performed anyway.

  **Human Review Update (2026-08-03):** The module owner clarified that the Payment Option checkbox list is **not** a fixed 5-value set — it inherits every **Active** record from the Payment Gateway module, so any Payment Gateway created there appears here automatically once active. The ~25 person-name/"m"/"f" checkboxes are therefore very likely Active Payment Gateway records with placeholder/test names, not a Branch-side data-binding defect. This reclassifies the underlying condition from a Branch `Bug` to an `Observation` about cross-module data hygiene, and updates the module's dependency model: `branch` reflects `payment-gateway`'s Active records live, exactly as it already reflects Supplier Credentials (per PRD.md SUP-05's cascade pattern). Not independently re-verified this run (e.g. by checking the Payment Gateway module's own record list for these exact names) — the disposition rests on Human Observation corroborating the original Direct Observation, not on a fresh live check of the Payment Gateway module, which was out of scope for this run.
- **Root Cause Hypothesis:** ~~Possibly the Payment Option control's options are sourced from a lookup/API call that returns entries from an unrelated or test-seeded table~~ — superseded by the Human Review Update above: the control's data source is the Payment Gateway module's Active records by design, not a misbound lookup. If the person-name entries are unwanted, the actual fix (if any) belongs to Payment Gateway master-data hygiene, not to the Branch screen's binding logic.
- **Occurrence Count:** 1
- **Evidence Links:** `before.png` (first observation, full Payment Option row visible), `failure.png` (second, independent observation after page reload, same anomaly present). No console/network capture attempted for this Finding — DOM/console capture was not wired into this run's ad hoc probe scripts, recorded as missing evidence, not fabricated.
- **Recommendation:** No action needed on the Branch screen itself. If the person-name/"m"/"f" Payment Gateway records are unwanted test data, that is a Payment Gateway module data-hygiene item, out of scope for this run — raise it there if it warrants cleanup. Consider a regression check asserting the Payment Option list only ever shows Payment Gateway records that are genuinely Active, to guard the "if only the payment gateway is active" rule the module owner described.
