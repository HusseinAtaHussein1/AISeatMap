# FINDING-013 — Stored Branch Email Password is returned to the browser and pre-filled into the Update form

- **Finding ID:** FINDING-013
- **Title:** Stored Branch Email Password is returned to the browser and pre-filled into the Update form in recoverable form
- **Category:** Security Concern → **Observation (Confirmed Intended Behaviour)**
- **Severity:** ~~High~~ → **N/A**
- **Severity Reason:** Severity no longer applies. The observed behaviour was dispositioned by the module owner on 2026-08-10 as **an intended business requirement, not a defect** (see Human Review Update below). Consistent with how this module's other intended-behaviour findings are recorded (FINDING-001, 005–010), a finding dispositioned as intended carries `N/A`. The original rating was High, on the Severity Matrix's Critical/High boundary for credential exposure.
- **Confidence Score:** 95% (that the behaviour occurs — unchanged and not in dispute; only its *disposition* changed)
- **Evidence Category:** Direct Observation
- **Status:** **Rejected — Confirmed Intended Behaviour** (was `Confirmed`, 2026-08-04 → 2026-08-10)

- **Human Review Update (2026-08-10, module owner):** *"it's not a bug but business needs."* The Update Branch form returning and pre-filling the stored Branch Email Password is **required behaviour**, not a defect. The observation below is factually unchanged and remains accurate; only its classification changes. **No fix is to be raised, and no test may assert the redacted behaviour as correct** without a new business decision reversing this one.

  **Accepted risk, recorded for the audit trail rather than as an objection.** Because the disposition makes the exposure intentional, these consequences are now *accepted properties of the design*, not open defects: any operator who can open Update Branch can recover the mail account's password with no elevated permission and no audit-worthy action; the value is transmitted to every client that opens the edit screen; on this environment (`http://192.168.1.70`, plain HTTP) it also transits unencrypted; and returning it at all implies the credential is stored reversibly rather than hashed. Recorded once, here, so a future reader knows the risk was seen and accepted deliberately — not missed.

  **Downstream consequence — needs a Stage 3 decision, not actioned here:** **TC-BR-077** ("Stored Branch Email Password is not recoverable from the Update form") asserts the *opposite* of this disposition. It is an approved test case whose expected result this decision invalidates. It has **not** been rewritten — redefining an approved Stage 3 test case is that stage's call, not Discovery's or Automation's. Flagged in `TestCases_Branch.md` for revision or retirement.
- **Business Risk:** The Branch Email account is a real mail account belonging to the organisation. Any operator who can reach the Update Branch screen — a routine, non-privileged admin task per US 8599/US 8606 — can recover that account's password without any elevated permission, without any audit-worthy action, and without it ever appearing on screen. It also means the password is transmitted to every client that opens the edit screen, widening exposure to anything observing the response (proxy, browser extension, shared workstation). On this environment that is plain HTTP, so it also crosses the network unencrypted.
- **Technical Risk:** Storing a password in a form that can be returned to a client implies it is held **reversibly** (encrypted-at-rest at best, plaintext at worst) rather than hashed. That is an architectural property, not a UI bug: no front-end change removes the underlying reversibility. It also indicates the edit endpoint serialises the full record without field-level redaction, so any other sensitive field on this or a sibling entity is likely handled the same way.
- **Module:** branch
- **Workflow:** Admin → Branch → Search Branch → edit pen → Update Branch → Branch Email Config Info
- **Description:** The Update Branch form's `Email Password` field is rendered as `<input type="password">` — masked on screen — but is **populated with the record's actual stored password**, which is present in the DOM and readable by any client-side inspection. The masking is presentational only.
- **Expected Behavior:** **Not defined in Project Context.** Neither US 8606 nor the carried-forward PRD sections state how a stored Email Password must be handled on re-edit. US 8606 says only "The user must enter an Email Password (free text, all character input & has a max length of 15 characters). (Mandatory)". The Project Context is silent on credential-handling policy for this field, so no documented requirement is contradicted — which is precisely why this is raised as a `Security Concern` rather than a `Bug`, and why it needs a human security decision rather than a defect fix ticket.
- **Actual Behavior:** On opening `/admin/branch/edit/{code}`, the `id-EmailPassword` element carries a non-empty value corresponding to the branch's stored email password. Confirmed populated across two independent fresh navigations and one hard reload. **The value itself is deliberately not recorded in this Finding, in this run's logs, or in any artifact** — only its presence and length were captured, per the platform's standing credential rule.
- **Steps to Reproduce:** 1) Log in as Super Admin. 2) Navigate to `/admin/branch`. 3) Click **Search**. 4) Click any row's edit pen. 5) Wait for the form to finish pre-filling. 6) Inspect the `Email Password` field's value via browser devtools (or toggle its input type). The stored password is present.
- **Investigation/Recovery Result:** Applicable category — "Suspected transient/environment state". Re-opened the edit screen via fresh navigation **twice**, plus one hard reload of the edit URL. The field was populated on all three occasions. The condition persists after recovery attempts, satisfying `Confirmed`'s recovery requirement.
- **Investigation Notes:** An intermediate probe reported the field as *empty*, which briefly suggested this was a false read. Polling showed that probe had sampled before the form finished rendering — the same sampling artifact that produced the (rejected) pre-fill false alarm described in `DiscoverySnapshot_UpdateBranch.md` §4. Once polled correctly, the field is populated within 500ms and stays populated. Deliberately **not** probed: whether the value is also present in the raw API response body, and whether other endpoints expose it. Both would sharpen the Finding, but capturing a response body containing a live credential would write that credential into this run's evidence, which the platform's credential rules forbid — the omission is recorded here rather than performed. The field carries no `autocomplete` attribute, so browser password managers may also capture it.
- **Root Cause Hypothesis:**
  - **Possible Root Cause:** Consistent with the edit endpoint returning the branch entity verbatim, with the front-end binding every returned field into its form control — no field-level redaction on the way out, and reversible storage making the plaintext available to return in the first place.
  - **Confidence:** 60%
  - **Supporting Evidence:** Every other field on the form pre-fills from the same fetch in the same 500ms window (`DiscoverySnapshot_UpdateBranch.md` §4), which is consistent with one whole-entity payload driving the whole form rather than a redacted projection.
  - **Unknowns:** Whether the password is stored encrypted-but-reversible or in plaintext; whether the API redacts for any other role; whether any server-side audit records the read. Server source, the storage schema, and the endpoint's response contract are needed to settle it — none is observable from the UI.
- **Occurrence Count:** 1
- **Evidence Links:** `failure.png` (full-page Update Branch screenshot with the field masked as the user sees it — the underlying value is **intentionally absent from all evidence**). No console log, DOM snapshot, HAR, or request/response summary is attached: each would embed the live credential in this run's artifacts, which the platform's credential rules prohibit. This is a deliberate, disclosed evidence gap, not an oversight — the presence/length observation transcribed above is the evidence.
- **Recommendation:** ~~Escalate to whoever owns platform security…~~ **Superseded 2026-08-10.** The module owner has dispositioned this as an intended business requirement, which answers the escalation this Finding was raised to prompt — no security fix is to be pursued and the original recommendation (blank field plus a "change password" affordance) is withdrawn. Two items remain, and neither is a defect fix: (1) **TC-BR-077 needs a Stage 3 revision or retirement**, since it asserts the redacted behaviour this decision rules out; (2) the credential-handling expectation should be written into the requirements, because `PRD_UserStories.md` US 8606 is currently **silent** on it — the absence of a documented rule is what caused this to be raised as a concern in the first place, and documenting the intended behaviour prevents the same finding being re-raised on the next Discovery pass.

  For the record, the original recommendation's underlying questions were never answered and are now moot as defect questions, but remain true as facts about the design: whether the password is stored reversibly, and whether the edit endpoint must return it. Both are settled by the disposition as "yes, by intent."
