# FINDING-014 — Records are filterable by Active/Inactive status, but that status is never displayed in the grid

- **Finding ID:** FINDING-014
- **Title:** Records are filterable by Active/Inactive status, but that status is never displayed in the grid
- **Category:** Requirement Gap
- **Severity:** N/A
- **Severity Reason:** Automatic `N/A` per §5.4 — Category is `Requirement Gap`, which asserts a documentation/specification gap rather than a defect, so it carries no impact-if-defect rating.
- **Confidence Score:** 96%
- **Evidence Category:** Direct Observation
- **Status:** Needs Human Review
- **Business Risk:** An operator filtering by `Both` (616 records) receives a mixed Active and Inactive result set with **no way to tell which is which** from the grid. Acting on the wrong record — editing or approving an inactive branch believing it active — is possible without any on-screen signal. The risk is real but its severity depends on how operators actually use the `Both` filter, which is a business question.
- **Technical Risk:** None identified — the status is stored and is demonstrably queryable (the filter partitions the set correctly). This is a display omission.
- **Module:** branch
- **Workflow:** Admin → Branch → Search Branch → Status filter + results grid
- **Description:** The Status radio filters on a record property (Inactive / Active / Both) that the results grid never renders as a column. The only status-like column is `Approval Status`, which is a **different axis** — it carries `Approved` / `Pending for approval` / `Rejected`.
- **Expected Behavior:** Two sources bear on this and they are recorded separately rather than merged. (a) PRD_UserStories.md US 7 §Search Result Grid enumerates the required columns and **does not include** an Active/Inactive Status column — so on the story's own terms nothing is missing. (b) PRD.md XC-07, carried into ProjectContext.md's PRD-sections row, states platform-wide that "Grid columns expose approval state to the operator: **Status** and **Approval Status** are distinct columns" — tagged `[V]`, verified by header assertions for both columns in other modules. Against XC-07 the Branch grid is non-conforming. **The Project Context does not resolve which source governs here**, which is why this is `Needs Human Review` and not a Bug.
- **Actual Behavior:** The grid renders six headers — `Code`, `Branch Name`, `Country Name`, `City`, `Approval Status`, `Actions`. There is no Active/Inactive Status column. Filtering by `Active` returns 491 records, `Inactive` 125, `Both` 616; the `Both` result set visibly mixes the two populations with no distinguishing column.
- **Steps to Reproduce:** 1) Log in as Super Admin. 2) Navigate to `/admin/branch`. 3) Select Status = **Both**. 4) Click **Search**. 5) Observe that the grid returns 616 records and no column indicates which are Active and which Inactive.
- **Investigation/Recovery Result:** Not applicable — a rendered header set is deterministic; no §5.7 recovery category matches. The header enumeration was nonetheless repeated across two independent sessions with identical results.
- **Investigation Notes:** Verified that the missing column is not responsive-hidden, using the same hidden-element enumeration described in FINDING-012 (all six headers `display: table-cell`, none with `offsetParent === null`). Confirmed the two axes are genuinely different rather than one column serving both: the Status **filter** partitions 491/125/616 arithmetically, while the `Approval Status` **column** independently carries `Approved` (110 of 120 sampled), `Pending for approval` (6) and `Rejected` (4). A record can therefore be Active-and-Pending or Inactive-and-Approved, and the grid shows only the second half of that pair. Deliberately **not** raised as part of FINDING-012 despite both being missing columns: FINDING-012's State column is required by the in-scope story and its absence is a straightforward contradiction, whereas this column is required only by a platform-wide cross-cutting rule the story is silent on — different evidence, different disposition, so merging them would obscure the fact that one is clear-cut and one is a judgement call. Also relevant to ProjectContext.md's RISK-BR-8: US 8599's business rule "Approving or rejecting a branch updates its status accordingly" is ambiguous as to **which** status it means, and this Finding shows the grid can only ever evidence the Approval Status half of that question.
- **Occurrence Count:** 1
- **Evidence Links:** `failure.png` (grid on Status=Both, showing the six headers and a mixed result set with no Active/Inactive indicator). The filter-count observations (491 / 125 / 616) and the approval-status distribution are transcribed in `DiscoverySnapshot_SearchBranch.md` §4 and §6.
- **Recommendation:** Put the question to Product as a single decision: should the Branch grid conform to XC-07 by exposing a Status column, or is US 8599's six-column set correct and XC-07 simply not universal? The answer also settles RISK-BR-8 for Test Design — until it is answered, Test Design should not author a case asserting that approve/reject changes the Active/Inactive status, because no UI surface would evidence such a change.
