# FINDING-016 — Credit Terms (Days) 7-digit cap makes Warning Prompt's documented 11-digit cap unreachable

- **Finding ID:** FINDING-016
- **Title:** Credit Terms (Days) 7-digit cap makes Warning Prompt's documented 11-digit cap unreachable
- **Category:** Requirement Gap
- **Severity:** N/A
- **Severity Reason:** Not a defect in the application's behaviour — a contradiction between two documented/clarified business rules. Severity is not assigned to a specification conflict; it needs a requirements decision, not a fix.
- **Confidence Score:** 100% (the contradiction is arithmetic — unchanged; only its disposition changed)
- **Evidence Category:** Human Observation
- **Status:** **Rejected — Dropped by module owner** (was `Needs Human Review`, filed and closed 2026-08-10)

- **Human Review Update (2026-08-10, module owner):** *"سيبك منهم ومتحطهمش في الاوتوميشن"* — leave these alone and keep them out of automation. Accordingly this Finding is closed and **none of the affected cases are automated**: `TC-BR-026` removed from the automation suite outright, `TC-BR-027` and `TC-BR-082` remain `Automation: Rejected`. All three Stage 3 test cases are retained, unchanged, in the manual suite.

  **Closed on instruction, not resolved.** The contradiction itself still stands in the documented requirements — Warning Prompt (Days) max 11 digits, must be less than Credit Terms (Days), and Credit Terms (Days) max 7 digits cannot all hold at once, since Credit Terms is Mandatory and its largest legal value (9999999) is smaller than any 12-digit Warning Prompt value. Nothing about that arithmetic changed; it is simply no longer being pursued. Recorded plainly so a later reader does not mistake "dropped" for "fixed". The 7-digit Credit Terms cap added to `PRD_UserStories.md` on the same day is left in place — it is a real, business-confirmed rule and correct to document regardless.
- **Business Risk:** Warning Prompt (Days)'s stated 11-digit maximum can never be exercised through the UI, so it is either dead specification or the cross-field rule is the only cap that actually governs the field. Until that is settled, no test can prove the 11-digit rule is enforced, and FINDING-004's defect claim cannot be closed either way.
- **Technical Risk:** None introduced by this finding itself. It does mean any test targeting Warning Prompt's 11-digit boundary is structurally unable to isolate a length-specific validation from the cross-field one.
- **Module:** branch
- **Workflow:** Admin → Branch → Create Branch → Branch Sales Configuration → Credit Terms (Days) / Warning Prompt (Days)
- **Description:** Two rules, taken together, cannot both be satisfied by any legal input. (1) Credit Terms (Days) has a maximum length of **7 digits** — a constraint confirmed by the business 2026-08-10 and **not documented anywhere in PRD_UserStories.md**, which states only "numeric input only … (Mandatory)". (2) Warning Prompt (Days) has a documented maximum length of **11 digits** and **must not be greater than Credit Terms (Days)** (PRD_UserStories.md US 5 §Branch Sales Configuration). Any Warning Prompt value large enough to test the 11-digit boundary needs 12+ digits, which is necessarily greater than the largest legal Credit Terms value (9999999, 7 digits). Credit Terms is Mandatory, so it cannot be left blank to sidestep the comparison. The cross-field rule therefore always fires for any Warning Prompt input in the range the 11-digit cap is about.
- **Expected Behavior:** The two documented constraints should be mutually satisfiable, or the specification should state which one governs when they collide.
- **Actual Behavior:** No legal (Credit Terms, Warning Prompt) pair exists that both satisfies the cross-field rule and reaches Warning Prompt's 11-digit boundary.
- **Steps to Reproduce:** Not a runtime reproduction — a specification comparison. 1) Read PRD_UserStories.md US 5 §Branch Sales Configuration (Warning Prompt: max 11 digits, must be less than Credit Terms; Credit Terms: numeric, Mandatory, no length stated). 2) Apply the business's 2026-08-10 clarification that Credit Terms caps at 7 digits. 3) Attempt to choose a Credit Terms value ≥ a 12-digit Warning Prompt value — no legal value exists.
- **Investigation/Recovery Result:** N/A — no execution was involved.
- **Investigation Notes:** Raised while reassessing TC-BR-026 against the new Credit Terms clarification, per explicit instruction not to invent a workaround but to flag the conflict. **TC-BR-026 is `Blocked — Needs Clarification` and its original Stage 3 business intent is preserved unchanged** (user instruction, 2026-08-10): an earlier revision of this finding recorded it as *rescoped* to assert only the field's own retained-value length regardless of which message appears — that was reverted, because narrowing the case that way would have redefined an approved test case around what automation could conveniently run, dropping the isolation from TC-BR-027's cross-field rule that is the case's actual objective. Its automation is `@Test(enabled = false)` with the body intact, so it runs unchanged once the rule is confirmed. No expected value was weakened, and no substitute Test Data was invented to make the case runnable.
- **Blocking Impact:** TC-BR-026 contributes no result at all while blocked — not a pass, not a failure. Warning Prompt (Days)'s documented 11-digit maximum therefore has **no test coverage**, and FINDING-004's length-cap defect claim cannot be confirmed or closed, in either direction, until this finding is resolved.
- **Occurrence Count:** 1
- **Evidence Links:** None captured — this is a documentation comparison, not an observed application behaviour. The Credit Terms 7-digit cap itself is business-stated (2026-08-10, this conversation) and has **not** been independently verified live against STG; verifying it is a follow-up, not an assumption to build on.
- **Recommendation:** Requirements/Stage 3 decision needed on two points. (1) Document Credit Terms (Days)'s 7-digit maximum in PRD_UserStories.md — it is currently absent. (2) Decide whether Warning Prompt (Days)'s 11-digit maximum is still a meaningful requirement given that the cross-field rule caps the field far below it in practice; if it is, state how it is intended to be validated, and if it is not, retire it so FINDING-004's regression case can be closed or rescoped accordingly.
