# FINDING-004

- **Title:** NDC has multiple distinct Admin-tier roles (Super Admin, Admin) with different feature access — Project Context describes only a single undifferentiated "NDC Admin" role
- **Category:** Requirement Gap
- **Severity:** N/A (Requirement Gap category, per §5.4)
- **Severity Reason:** Not applicable — Requirement Gap categories carry no impact-if-defect rating; this documents a gap in the requirement source's role model, not an application defect.
- **Confidence Score:** 90%
- **Evidence Category:** Human Observation (§17) — this specific fact was reported directly by the human operator (acting in the project's Business Analyst/Product Owner role, per the Run Manifest), not observed by the agent in the live application. Per §18, this caps Status below `Confirmed` regardless of clarity.
- **Status:** Needs Human Review
- **Business Risk:** Both in-scope User Stories (T3002-066, T3087) are written "As an NDC Admin," with no indication of which Admin tier. If Test Design assumes the wrong role for a test case (e.g., attempts a Booking Cycle test under Super Admin), the test will fail for a reason unrelated to the feature under test — a false negative that wastes investigation time and could be misattributed to a real defect.
- **Technical Risk:** If role-based access control gates are stricter than currently documented anywhere, other in-scope screens (Credential Routes Filter, Airport, Supplier Credentials, Airline, Booking-Mid Office) may behave differently, or be entirely inaccessible, under one role vs. the other — not yet confirmed one way or the other beyond the Booking Cycle example.
- **Module:** Global — role/access-control model, cross-cutting all in-scope modules
- **Workflow:** Login / role selection
- **Description:** Project Context v1 §4 ("Roles & Credentials Required") describes a single "NDC Admin" role, backed by one confirmed account (`E.Saady`). During this run, the human operator clarified directly (2026-07-11) that NDC actually has at least two distinct Admin-tier roles — **Super Admin** (`odeysysadmin`) and **Admin** (`e.saady`) — with different feature access. Example given: Super Admin **cannot** complete the Booking Cycle (cannot book a ticket), while (by implication) Admin can. This is consistent with, and now explains, FINDING-001 (nav bar difference) and FINDING-002 (identity difference) observed earlier in this same run.
- **Expected Behavior:** Per `projects/NDC/artifacts/context/NDC_ProjectContext.v1.md` §4: a single "NDC Admin" role is described, with `E.Saady` as its confirmed account. The Project Context does not distinguish Super Admin from Admin, and does not state which tier either User Story's "As an NDC Admin" actor refers to.
- **Actual Behavior:** At least two distinct Admin-tier roles exist live: Super Admin (`odeysysadmin`, observed with an 11-item nav bar, per this run's screenshots) and Admin (`e.saady`, previously documented with a full 13-item nav bar). Per stakeholder statement, Super Admin cannot complete the Booking Cycle.
- **Steps to Reproduce:** N/A — this Finding is a documentation/requirement-model gap, not a reproducible application behavior; the underlying facts (role names, the Booking Cycle restriction) were stated directly by the project stakeholder rather than observed live in this run.
- **Investigation/Recovery Result:** Not applicable — not a failure condition subject to the Investigation & Recovery Engine.
- **Investigation Notes:** Not yet independently verified live (e.g., attempting a booking search/booking flow under Super Admin to directly observe the restriction) — in scope for the Booking-Mid Office exploration step later in this run. Full permission differences beyond the Booking Cycle example are unknown.
- **Root Cause Hypothesis:** *(omitted — this Finding's Description already states the confirmed fact directly; no further hypothesis needed.)*
- **Occurrence Count:** 1
- **Evidence Links:** No screenshot evidence — this Finding is sourced from a direct, in-conversation stakeholder statement (2026-07-11), not a captured application state. Recorded per §5.11's floor for Requirement Gap (screenshots where a live surface exists) — no live surface exists for a "role model" as such, so this is documented via the stakeholder's own statement instead, per §5.10's rule to name what's missing/why rather than fabricate.
- **Recommendation:** (1) Update `projects/NDC/run_configuration.md`'s Credentials table to record both roles explicitly (Super Admin/`odeysysadmin`, Admin/`e.saady`) with their known permission differences. (2) When Project Context is next revised, §4 should name both roles and clarify which tier each User Story's "NDC Admin" actor refers to. (3) Test Design (Stage 3) should assign an explicit role to every test case involving Booking-Mid Office/Portal Booking Module or any other feature suspected of being role-gated, rather than assuming "NDC Admin" is a single interchangeable role. (4) When this run reaches Booking-Mid Office exploration, use the Admin (`e.saady`) credential specifically to observe the actual booking/search-results flow, since Super Admin cannot complete it.
