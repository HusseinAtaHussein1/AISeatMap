## What Happened

Two independent elements in `Agency_Page.java` — the Branch dropdown (`Lst_Branch`) and the B2B
Business Type radio (`Rbtn_BusinessTypeB2B`) — were both originally locating the underlying,
visually-hidden native `<input>` PrimeNG renders for accessibility (`id-Branch`,
`id-AgencyBusinessType-B2B`), and clicking it directly. Both failed with
`ElementNotInteractableException`. Repaired by re-targeting the click at the semantic PrimeNG
wrapper element that actually receives pointer events — `p-dropdown[.//input[@id="..."]]` for the
dropdown, `p-radiobutton[.//input[@id="..."]]` for the radio — matching the convention this same
package's own `Branch_Page.java` already used for its Country/State/City dropdowns and
Active/Inactive/Both radios. The Branch dropdown fix surfaced a second, distinct bug once it started
working (see REP-005) — repairs applied in this pass did not necessarily fully resolve a test case
in one iteration; each fix can expose a previously-unreached downstream issue.

## General Pattern (candidate for platform promotion — not yet promoted, needs explicit approval)

**Whenever a PrimeNG-rendered form control's native `<input>`/`<textarea>` is not directly
interactable, target the PrimeNG custom-element wrapper instead of the native input it contains.**
Applies at minimum to `p-dropdown`, `p-radiobutton`, `p-checkbox`, `p-multiselect` — every one of
these components renders a hidden or non-clickable native input paired with a visible custom
element that owns the actual click/keyboard handling. A locator built from the input's `id` alone
(`//input[@id="..."]`) finds the right *element to identify*, but is frequently the wrong element to
*click* — wrap it: `//{prime-ng-tag}[.//input[@id="..."]]`.
