- **Finding ID:** FINDING-006
- **Title:** Agency Add "Contact person" field silently strips Arabic-script characters, client-side, even on direct programmatic value assignment
- **Category:** Application Behavior (reclassified from an Automation-tooling assumption — see Root Cause below)
- **Severity:** Medium
- **Severity Reason:** Silent data loss (no validation message, no error) for any contact name containing Arabic script — a realistic input for a UAE/Egypt-market NDC deployment. Not Higher because it does not block the workflow (the record still submits) and no corruption/crash occurs, only silent truncation of one script.
- **Confidence Score:** 95% — directly reproduced by bypassing Selenium entirely (raw `element.value = ...` + dispatched `input`/`change` events via Playwright's `page.evaluate`) and still observing the Arabic-only value read back as an empty string.
- **Evidence Category:** Direct Observation (live re-test against STG, 2026-07-13) + prior Execution evidence (EXEC-20260712-002-001, TC-AGENCY-005, both native `sendKeys` and an earlier JS-injection attempt)
- **Status:** Resolved — Confirmed By Design (2026-07-18, user/business stakeholder confirmed the application does not support Arabic-script input; not an application defect)
- **Business Risk:** Medium — any Agency/Branch/Staff Contact Person name containing Arabic script is silently dropped, not rejected with a validation message a data-entry user could act on.
- **Technical Risk:** N/A — client-side only; not yet confirmed whether the same stripping also happens server-side (a value bypassing the Angular form entirely, e.g. a direct API call, was not tested this pass).
- **Module:** Admin / Agency (Add form) — "Contact person" field (`#id-Contactperson`)
- **Workflow:** Add Agency (owner/contact details step); the same input component may be shared by other Contact-person-style fields elsewhere in Admin — not yet cross-checked.
- **Description:** TC-AGENCY-005 (`agencyTestData.json`'s `unicodeContactPerson`: `"القاهرة_测试_QA_SPIKE"`) originally failed with native `sendKeys` (Arabic dropped, CJK preserved) — Round 1 of the Automation Repair Loop (EXEC-20260712-002-001) attributed this to a Selenium/ChromeDriver bidi-input limitation and proposed a JS `value` + `dispatchEvent` workaround as the fix. Round 2 (2026-07-13) re-tested that exact workaround live and it **also** produced an empty result for Arabic-only input (`"القاهرة"` → `""`), and the same mixed string still lost only the Arabic portion (`"القاهرة_测试_QA_SPIKE"` → `"_测试_QA_SPIKE"`). Since this reproduces with zero Selenium/WebDriver involvement — the value was set directly on the DOM element via `page.evaluate` — the original "Selenium tooling limitation" diagnosis is not the true root cause. The field's own HTML attributes (`maxLength: -1`, `pattern: null`, no `inputmode`) show no native HTML restriction either, meaning the stripping happens inside Angular's own reactive-form value pipeline (a custom `ControlValueAccessor`, an `input`-event handler, or a formatter) that discards Arabic-range characters on write, before the value is ever committed to the control's underlying model.
- **Expected Behavior:** Not defined in the Project Context or any approved requirement — whether Arabic-script contact names must be supported is a genuine open question, not something this platform can infer.
- **Actual Behavior:** Confirmed via three independent methods, all client-side, all bypassing Selenium's own input mechanism at least once: (1) Playwright native `type()` (real key events) → empty; (2) direct JS `.value` assignment + `input`/`change` events → empty; (3) same JS assignment with the full mixed-script string → only the Arabic segment dropped, CJK and ASCII segments preserved.
- **Steps to Reproduce:** Open Admin → Agency → Add agency; in the Contact person field, run in DevTools console (or via any automation): `el.value = 'القاهرة'; el.dispatchEvent(new Event('input', {bubbles:true})); el.dispatchEvent(new Event('change', {bubbles:true}));` then read `el.value` — observe it is `""`.
- **Investigation/Recovery Result:** Investigation concluded this is not automation-repairable — no locator, wait, or input-mechanism change on the automation side can make the application accept a value it itself discards. Recommending Automation Decision be revised from "Generate New Automation"/repair-in-progress to a **Partially Automatable** disposition for the Unicode assertion specifically: automate the "field accepts CJK/Latin input" portion, and change the Arabic-specific assertion to an explicit, documented "capture observed value, do not hard-assert equality" pending a human decision on expected behavior (mirrors the pattern already used for TC-AGENCY-002/004's validation-text capture).
- **Investigation Notes:** No server-side/API-level verification performed this pass (would require inspecting the network request payload independent of the Angular form, out of scope for this diagnosis).
- **Root Cause Hypothesis:** An Angular reactive-form directive or custom input formatter applied to this field (possibly shared platform-wide for "name"-style fields) filters input by Unicode range, allowing Latin/CJK but rejecting Arabic (and possibly other RTL or non-Latin/non-CJK scripts, untested). Confidence: 60% — the asymmetric Arabic-vs-CJK result is consistent with a script-range filter, but the exact implementation (which directive, which regex) was not inspected in the Angular source (not accessible to this platform).
- **Occurrence Count:** 2 (original Execution + this Round 2 re-diagnosis, both against the same field)
- **Evidence Links:** `agencyTestData.json`'s `unicodeContactPerson`; `ExecutionResults.md` §Repair Summary #4 (original diagnosis); this run's live re-test via `tools/browser_driver` (Playwright), 2026-07-13 — screenshot `agency-contact-person-unicode.png` (scratchpad, not retained per Debug Mode Off convention — reproducible via Steps to Reproduce above).
- **Recommendation:** (1) Ask a human/business stakeholder whether Arabic-script contact names must be supported — if yes, this is a genuine Application defect to log against the app team; if the field is intentionally Latin/CJK-only, TC-AGENCY-005 should be redesigned to assert the *actual* intended behavior instead of an assumption. (2) Until that's answered, keep TC-AGENCY-005 as Partially Automatable — automate the CJK/Latin-acceptance assertion, drop the hard-equality assertion on the Arabic segment, and log the observed (not expected) value.
- **Resolution (2026-07-18):** User/business stakeholder confirmed the application intentionally does not support Arabic-script input — this is expected behavior, not a defect. No app-team escalation needed. TC-AGENCY-005 has been redesigned per the Recommendation's alternative branch: it now asserts the actual intended behavior directly (Arabic segment stripped, CJK/Latin segments preserved) as a real Generate/pass-fail check rather than a capture-only Partially Automatable disposition. See `test_design/TestCases_Agency.md` TC-AGENCY-005 and `knowledge_base/business_rules/BR-001.md`.
