# FINDING-003

- **Title:** Credential Routes Filter's Routes list is hard-capped at 50 entries per rule — not documented anywhere in the Project Context or source User Stories
- **Category:** Requirement Gap
- **Severity:** N/A (Requirement Gap category, per §5.4)
- **Severity Reason:** Not applicable — Requirement Gap categories carry no impact-if-defect rating; this documents a coverage gap in the requirement source, not an application defect.
- **Confidence Score:** 85%
- **Evidence Category:** Human Observation (§17)
- **Status:** Needs Human Review
- **Business Risk:** If a real customer/rule legitimately needs more than 50 origin-destination route pairs under one Supplier+Credential combination (plausible for a large route network), the cap would silently block them with no documented justification or override path observed yet.
- **Technical Risk:** An undocumented hard limit suggests a fixed-size backing structure or validation constant; if it's arbitrary rather than a deliberate product decision, it may need to be configurable (cf. `Admin Settings`'s existing pattern of exposing similar limits like `MAX_SUPPLIER_RESULTS` as configurable key/value settings, per `architecture.md`).
- **Module:** Master → Supplier → Credential Routes Filter (Add and Edit screens)
- **Workflow:** Adding/editing routes within a Credential Routes Filter rule
- **Description:** Both the Add Routes Filter screen (0 routes) and the Edit Routes Filter screen for the existing Galileo/Galileo Live UAE rule (1 route) display a counter in the Routes section reading `{count} / 50`, indicating a maximum of 50 route entries per rule. Neither T3002-066 nor T3087 (the two source User Stories) nor the approved Project Context v1 mentions any numeric cap on the Routes list.
- **Expected Behavior:** Not defined in Project Context — Project Context §1/§6 discusses the Routes list's *shape* (single list, Whitelist/Blacklist mode) but states no maximum count.
- **Actual Behavior:** UI displays and presumably enforces a 50-route-per-rule cap, observed identically on both the Add screen (`0 / 50`) and the Edit screen for record `287` (`1 / 50`).
- **Steps to Reproduce:** Navigate to Master → Supplier → Credential Routes Filter → Add Routes Filter (or Edit an existing rule) → observe the counter beneath the Routes list.
- **Investigation/Recovery Result:** Not applicable — this is a static UI observation (a displayed counter), not a failure/error condition. Whether the cap is actually *enforced* at 50 (e.g., the `Add` button for a 51st route greys out or errors) was not tested this session — no rule currently has more than 1 route, so testing the actual boundary would require adding up to 50 routes, which is a mutating action not authorized under the current Read-only environment constraint (Project Context §5).
- **Investigation Notes:** This resembles a Validation-category boundary condition (§5.8), but exercising it (adding 50+ routes) requires mutating the shared staging environment, which Project Context §5 explicitly prohibits this run. Recorded here as an observed UI signal and flagged for Test Design as a boundary-value test case to design (not execute) rather than a boundary this run could safely probe live.
- **Root Cause Hypothesis:** *(omitted — no evidence yet supports a specific explanation for why 50 was chosen; recording the fact of the cap, not speculating on its origin.)*
- **Occurrence Count:** 1 (same cap value observed identically in 2 places — Add and Edit — treated as one underlying condition)
- **Evidence Links:** Full-page screenshots of Add screen (`0 / 50`) and Edit screen for record 287 (`1 / 50`) — transcribed in `CredentialRoutesFilter_AddScreen.md` and `CredentialRoutesFilter_EditScreen.md`. Raw image files not independently persisted (see FINDING-001's Evidence Links note).
- **Recommendation:** Flag for the Business Analyst/Product Owner to confirm whether 50 is an intentional, documented business rule (and if so, add it to the Project Context on the next revision) or an arbitrary technical constraint that should be configurable. Test Design (Stage 3) should add a boundary-value test case for "51st route rejected / 50th route accepted" as a **designed-but-marked-assumption-based** test (per the Read-only constraint, this cannot be executed against staging without mutation authorization) rather than skip it.
