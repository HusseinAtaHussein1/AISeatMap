# FINDING-001

- **Finding ID:** FINDING-001
- **Title:** Emoji in Username field triggers generic server error instead of "Invalid credentials"
- **Category:** Security Concern
- **Severity:** Medium
- **Severity Reason:** Matches no Critical/High criterion (login remains possible for normal input; no core workflow is blocked); matches the Medium criterion "validation issues / business rule inconsistencies" — the login endpoint's input-handling path behaves inconsistently for one class of otherwise-valid text input.
- **Confidence Score:** 95%
- **Status:** Needs Human Review
- **Business Risk:** Low direct business impact (emoji usernames are not a real-world credential pattern for this system), but the underlying inconsistent error handling is a code-quality/robustness signal that could mask other input-handling defects with real business impact.
- **Technical Risk:** Medium — suggests an unhandled exception path (most likely a 4-byte-UTF8/utf8mb4 vs 3-byte encoding mismatch at the username-lookup step) that a malicious actor could potentially use to distinguish this input class from normal invalid-credential handling, and that indicates at least one code path lacks graceful error handling.
- **Module:** Login / Authentication & Access
- **Workflow:** Login form credential submission (PRD §5.1 FR-1)
- **Description:** Submitting a login attempt with an emoji character in the Username field produces a generic `"Unexpected error occurred"` alert instead of the standard `"Invalid credentials"` message returned for every other tested invalid-credential input.
- **Expected Behavior:** Not defined in Project Context for this specific input class. PRD FR-1 only states "the system must present a login form"; it does not specify error-handling behavior for malformed/unusual credential input.
- **Actual Behavior:** Username = `😀`, Password = any normal string → alert text `"Unexpected error occurred"`. Isolated to the Username field (Password = `😀` with a normal Username → normal `"Invalid credentials"`). Reproduced identically on 2 of 2 attempts this run (fresh evidence, independent of `RUN-20260706-001`'s prior, still-unapproved observation of the same underlying condition).
- **Steps to Reproduce:** 1) Navigate to the Login page unauthenticated. 2) Enter `😀` in Username. 3) Enter any string in Password. 4) Click Login. 5) Observe `"Unexpected error occurred"`.
- **Investigation/Recovery Result:** Failure category not listed in the Investigation & Recovery Engine (§5.7) — not a clean match for Navigation/Timeout/Validation-failure/Network-failure/Unexpected-UI-rendering. Per the Engine's default rule, treated as "No retry" — validated by reproducing twice in this run (plus a third, isolating reproduction with the emoji moved to the Password field, which did NOT reproduce the error, confirming the anomaly is Username-field-specific).
- **Investigation Notes:** Boundary sweep this run: emoji (username) → error, reproduced 2/2; emoji (password only) → normal, confirming isolation; SQL-injection-style payload (both fields) → normal "Invalid credentials," no bypass. Special-characters/XSS and long-input boundary conditions were not independently re-tested this run (time-scoped decision) — both were confirmed clean (no anomaly) under `RUN-20260706-001`'s exploration of the same Login form, which this run's own Investigation Notes cite as supporting context, not as a substitute for this run's own evidence on the categories it did test.
- **Root Cause Hypothesis:** *Possible Root Cause:* consistent with a backend database column encoding limitation (e.g., `utf8` (3-byte) vs `utf8mb4` (4-byte)) rejecting the emoji character during a username lookup, surfaced via a generic exception handler. *Confidence:* 55% (plausible and consistent with the isolation result, but not independently confirmed against server internals). *Supporting Evidence:* `failure.png`; the error is specific to the Username field only, consistent with a lookup/query operating on that field specifically. *Unknowns:* actual database schema/column encoding; whether the exception is logged server-side with more detail than the generic user-facing message.
- **Occurrence Count:** 1 (2 reproductions of the same underlying condition this run, consistent with the same condition observed independently in `RUN-20260706-001`)
- **Evidence Links:** `failure.png` (the "Unexpected error occurred" state). Console captured at failure state: 0 errors/0 warnings (not saved as a separate file — identical null result to what would be redundant to store).
- **Recommendation:** Confirm with the development team whether this is a caught exception with a known cause (e.g., encoding mismatch). If so, decide whether the generic fallback message is an acceptable permanent behavior (arguably fine from a security-disclosure standpoint) or whether more graceful input validation should reject non-BMP characters before they reach the failing code path.
