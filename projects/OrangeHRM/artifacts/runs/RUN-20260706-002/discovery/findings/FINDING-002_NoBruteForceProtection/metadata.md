# FINDING-002

- **Finding ID:** FINDING-002
- **Title:** No brute-force/lockout protection on repeated failed logins
- **Category:** Security Concern
- **Severity:** Low *(see Investigation Notes — the source PRD independently rates this same underlying condition High)*
- **Severity Reason:** Does not cleanly match Critical (no breach occurred), High (no core workflow blocked — the account remained usable), or Medium (not a validation/business-rule inconsistency) criteria. Defaulted to Low per the Severity Matrix's explicit ambiguity rule.
- **Confidence Score:** 95%
- **Status:** Needs Human Review
- **Business Risk:** Exposes the Admin account (and by extension any account) to unthrottled credential-stuffing/guessing attempts from any source that can reach the login endpoint.
- **Technical Risk:** No server-side rate-limiting signal observed (no `Retry-After`/`X-RateLimit-*` headers, no increasing latency, no CAPTCHA challenge) across 3 consecutive failed attempts against a known-valid username.
- **Module:** Login / Authentication & Access
- **Workflow:** Repeated login-failure handling (PRD §10 SR-5)
- **Description:** 3 consecutive failed login attempts against the known-valid `Admin` username, each with a different wrong password, produced no lockout, delay, CAPTCHA, or rate-limit signal of any kind.
- **Expected Behavior:** Not asserted as a hard requirement by the Project Context — it directs the Explorer Agent to "re-attempt a small number of failed logins and observe" rather than asserting a control must exist. PRD §10 SR-5 documents this as a pre-existing, already-known risk.
- **Actual Behavior:** 3× `POST /web/index.php/auth/validate` (Username=`Admin`, wrong passwords) → each returned an identical `302` redirect with no rate-limiting headers; identical `"Invalid credentials"` message each time; no increasing delay.
- **Steps to Reproduce:** Submit `Admin` + wrong password 3 times in quick succession; observe no lockout/CAPTCHA/delay appears on any attempt.
- **Investigation/Recovery Result:** Not applicable — this Finding's investigation is itself the deliberate multi-attempt probe called for by the Project Context; each attempt was validated directly (identical, unambiguous result), no recovery/retry needed to confirm what was observed.
- **Investigation Notes:** This run used 3 attempts (vs. 5 in `RUN-20260706-001`'s independent probe of the same underlying condition under the Login-only Project Context) — still within the Project Context's "small, reasonable number of probe attempts" ceiling. **Severity ambiguity, recorded explicitly per the Severity Matrix's own rule:** this condition is the *absence* of a security control, which doesn't cleanly fit any of this agent's own Critical/High/Medium/Low criteria; the default is Low. The source PRD (§14 Risks) independently rates this same condition as **High**-impact. This Finding does not resolve that discrepancy on its own authority — it surfaces it for the human reviewer.
- **Root Cause Hypothesis:** *(omitted — this is a confirmed absence of a UI-visible control, not a symptom requiring root-cause investigation; whether server-side protection exists without UI feedback is exactly the open question this Finding raises, not something a root-cause hypothesis would resolve.)*
- **Occurrence Count:** 1
- **Evidence Links:** `after.png` (state after the 3rd attempt). Network trace of the 3 `POST /auth/validate` requests confirmed via live inspection during this run (all `302`, no rate-limit headers) — not saved as a separate log file for this run (evidence is the reproducible pattern itself, already documented above and in `discovery/login_bruteforce_probe.md`).
- **Recommendation:** Confirm with the Product Owner / Security stakeholder whether server-side rate-limiting/lockout/CAPTCHA is intentionally deferred for this open-source demo build, or is a genuine gap. If deferred intentionally, this Finding's tracked severity could reasonably be downgraded to match; if not, treat per the PRD's own High rating.
