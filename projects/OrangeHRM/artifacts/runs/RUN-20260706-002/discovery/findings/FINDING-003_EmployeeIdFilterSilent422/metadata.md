# FINDING-003

- **Finding ID:** FINDING-003
- **Title:** Employee List "Employee Id" filter silently fails (HTTP 422, no user feedback) for values over 10 characters
- **Category:** Bug
- **Severity:** Medium
- **Severity Reason:** Matches the Medium criterion "Validation issues / business rule inconsistencies" — a validation boundary is enforced server-side but not surfaced to the user, and the failure mode leaves the UI in a misleading state. Does not reach High (Employee List itself remains usable for every other input) or Critical.
- **Confidence Score:** 98%
- **Status:** Confirmed
- **Business Risk:** A user searching by a long Employee Id (or accidentally pasting extra characters) gets no error and no indication their search didn't run — the screen keeps showing the previous, unfiltered/broader result set (e.g., "(95) Records Found") as if it were the search result, which could mislead a user into believing an ID doesn't exist when the search in fact never executed, or vice versa into believing a filtered result is accurate when it is stale.
- **Technical Risk:** Confirms the `employeeId` query parameter has a server-side max length of exactly 10 characters, enforced by the backend API (which returns a well-formed, structured `422` error: `{"error":{"status":"422","message":"Invalid Parameter","data":{"invalidParamKeys":["employeeId"]}}}`) — but the frontend has **no client-side max-length constraint on the input field** and **does not handle the API's 422 response at all**, silently swallowing it and leaving the previous result set on screen.
- **Module:** PIM — Employee Management (Employee List filter)
- **Workflow:** Employee List search/filter (PRD FR-6)
- **Description:** Entering an Employee Id filter value longer than 10 characters and clicking Search causes the underlying API request to fail with `422 Unprocessable Entity`. The UI shows no error message and no "No Records Found" state — it simply leaves whatever result set was already on screen (in this case, the full unfiltered "(95) Records Found" list) displayed, unchanged, giving no indication that the search failed.
- **Expected Behavior:** Not explicitly defined in the Project Context/PRD for this exact boundary (PRD FR-6 states the filter field exists; it does not specify a max length or required error-handling behavior). The reasonable baseline this Finding compares against is the application's own correct behavior for every other tested input (see Actual Behavior) — a search that doesn't match any record should show "No Records Found," and a search that fails outright should show *some* indication of failure, neither of which happens here.
- **Actual Behavior:** Isolated via a systematic boundary sweep of the Employee Id filter:

  | Value | Length | Result |
  |---|---|---|
  | `999999` (numeric, nonexistent) | 6 | `200 OK` → "No Records Found" (correct) |
  | `ABC123` | 6 | `200 OK` → "No Records Found" (correct) |
  | `ABC-123` | 7 | `200 OK` → "No Records Found" (correct) |
  | `AAAAAAAAAA` | 10 | `200 OK` → "No Records Found" (correct) |
  | `AAAAAAAAAAA` | **11** | **`422`** → UI still shows "(95) Records Found" (stale, incorrect — no error shown) |
  | `AAAAAAAAAAAA` | 12 | **`422`** → same silent-failure behavior |
  | `ZZZ-NONEXISTENT-99999` | 22 | **`422`** → same silent-failure behavior (the value that first surfaced this Finding) |

  The failure is a pure **length** boundary at 11 characters — not related to hyphens, letters-vs-digits, or any other character-class property (confirmed by `ABC-123` at 7 characters succeeding despite containing a hyphen, while `AAAAAAAAAAA` at 11 characters with no special characters at all still fails).
- **Steps to Reproduce:** 1) Log in, navigate to PIM > Employee List. 2) Expand the search filters. 3) Enter any string of 11 or more characters into the "Employee Id" field. 4) Click Search. 5) Observe: no error message appears, and the record count/list shown does not change to reflect a failed or empty search.
- **Investigation/Recovery Result:** Failure category: Validation failure (a value the field should reject) — per the Investigation & Recovery Engine, "No retry — validation behavior is deterministic." Validated by reproducing the exact boundary 3 times (11, 12, and 22 characters, all `422`) and confirming the negative case (10 characters, `200`) twice (once as `AAAAAAAAAA` directly, once via the network log for the same request).
- **Investigation Notes:** This is a Validation-category candidate; per Investigation Mode, the relevant boundary (long input) was the one that surfaced this Finding in the first place, so the "boundary sweep" *is* this Finding's own investigation, run as a binary search (12 → 10 → 11 characters) to find the exact threshold rather than a fixed generic long-input probe. Other Validation boundary conditions (empty, unicode, emoji, SQL injection payload, special characters) were not separately re-tested against this specific field within this Finding's scope, since the anomaly was already fully explained by length alone — re-testing those categories against this field is left to the Test Design Agent's own systematic Negative Test Generation Engine coverage, not repeated here.
- **Root Cause Hypothesis:** *Possible Root Cause:* the `employeeId` filter parameter is likely validated server-side against the same length constraint as the underlying Employee Id database column (a `varchar(10)` or equivalent), which is correctly enforced by the API layer — but the frontend was never updated to add a matching client-side `maxlength` attribute or to handle a `422` response from this specific endpoint, unlike other forms in the application that do show inline validation. *Confidence:* 70% (the exact 10-character threshold and the well-formed, parameter-specific error response make a length-validated column a strong fit; not independently confirmed against the actual schema). *Supporting Evidence:* the precise, reproducible 10/11-character boundary; the structured error body naming `employeeId` specifically. *Unknowns:* the actual database column definition; whether other filter fields (Job Title, Sub Unit, Supervisor Name) have similar unhandled length limits (not tested in this run — flagged as a Test Gap in the Coverage Summary).
- **Occurrence Count:** 1 (3 reproductions of the same underlying condition at different input lengths, all above the same 10-character threshold — counted as one Finding per Duplicate Detection, not three)
- **Evidence Links:** `failure_22chars.png` (initial discovery, value `ZZZ-NONEXISTENT-99999`), `failure_11chars.png` (the precise boundary case), `comparison_numeric_nonexistent_correct.png` (correct behavior for a valid-length nonexistent value, for contrast). Network response body for the 11-character case captured inline above (`{"error":{"status":"422",...}}`) — not saved as a separate file since it is fully quoted in this metadata.
- **Recommendation:** Add a client-side `maxlength="10"` (or the actual correct limit) constraint to the Employee Id filter field, and/or add error handling for a failed search request that shows the user a clear message (e.g., "Employee Id must be 10 characters or fewer") instead of silently leaving stale results on screen. Consider auditing the other Employee List filter fields (Job Title, Sub Unit, Supervisor Name, Employee Name) for the same class of issue, since this run did not test them for it (see Coverage Summary, Test Gap).
