# 1. Component Name

**Run Manager**

# 2. Purpose

The Run Manager is an orchestration component responsible for preparing, organizing, monitoring, and finalizing every execution run of the Agentic AI Testing Platform pipeline.

**It is not an AI Agent.** It never analyzes software behavior, never forms an opinion about whether observed behavior is correct, never generates Findings, and never generates test cases. It has no judgment role anywhere in the pipeline. Its entire responsibility is mechanical: give every run a unique identity, a well-organized workspace, and a running record of what happened — nothing about *whether* what happened was good or bad.

Where the seven Agents (Project Context, Explorer, Test Design, Manual Execution, Automation, Automation Execution, Reporting) answer "what does the application do, and what should be tested, manually validated, built, run, and reported," the Run Manager only answers "which run is this, where does its output go, and what state is it in."

# 3. Non-Responsibilities

To keep this component's boundary unambiguous, the Run Manager explicitly must **not**:

- Analyze, interpret, or judge application behavior.
- Generate, classify, score, or triage Findings (that is the Explorer Agent's responsibility — see `.claude/skills/explorer-skill/SKILL.md`).
- Generate, design, or modify test cases (Test Design Agent) or automation scripts (Automation Agent).
- Decide whether a run "passed" or "succeeded" in a quality sense — it records mechanical status (§8), not a verdict.
- Modify the content of any artifact an Agent produces.
- Substitute for, or bypass, any Human Review / Automation Approval checkpoint defined in `workflows_and_pipelines/pipeline/pipeline.md` §5.

**Note on the run folder name, Title, and Description (§5, §7):** generating these is mechanical *selection/formatting* of context that already exists elsewhere (the Run Scope, a User Story/Bug ID, a Feature/Module name) via a deterministic function (§5.5) — never an analytical judgment about the application under test, and never an AI-generated summary. It does not cross into Findings, test-case generation, or quality verdicts, and it does not weaken the boundary in this section.

# 4. Responsibilities

The Run Manager must:

1. **Generate a self-descriptive run folder name** for every execution run, per the naming convention in §5 — always by calling `platform_core/tools/run_manager` (§5.5), never hand-formatted.
2. **Generate a Run Title and Description** (§7) — a short human-readable title and a longer descriptive summary of the run's objective, generated from the same Scope/Target context as the folder name.
3. **Validate filesystem-safe naming** — the naming utility itself sanitizes every segment (§5.5); the Run Manager must not bypass it and hand-format a folder name directly.
4. **Prevent duplicate folder names** — confirm the resulting Run Workspace folder name does not already exist before creating it; the utility appends a deterministic numeric suffix on collision (§5.5).
5. **Create the Run Workspace** — the directory structure in §6 — before any Agent begins work for that run.
6. **Generate Run Metadata** (`run.json`, §7) at the start of the run and keep it current as the run progresses.
7. **Provide workspace paths to downstream agents** — the concrete, run-scoped paths each Agent should treat as its working directory for that run's artifacts.
8. **Track execution status** — maintaining the run's current state from the Execution Status enum (§8) as the run moves through the pipeline.
9. **Maintain artifact organization** — ensuring every artifact produced during the run lands in the correct subdirectory of the Run Workspace (§6), without altering the content of any artifact.
10. **Publish a Run Summary** (`run_summary.md`, §9) once the run reaches a terminal status.

# 5. Run Naming Convention

**Revision note (2026-07-23, index prefix added 2026-07-27):** this revision replaces the `RUN-YYYYMMDD-XXX[-slug]` folder-naming scheme (§5.1/§5.2 in every prior revision of this document) with a self-descriptive convention that encodes the run's index, Scope, and Target directly in the folder name, so a run can be identified without opening it. Folder names are generated by calling the reusable module at `platform_core/tools/run_manager/` (§5.5) — never hand-formatted by an agent and never an AI-generated slug (the previous Display Name concept is retired; it was never actually produced by any real run — see §5.6). No existing run folder is renamed by this revision itself; see §5.6 for how legacy folders are handled.

## 5.1 Folder Name Format

```
run-NNN__YYYY-MM-DD_HH-mm-ss__[Scope]__[Module-or-UserStory]
```

- `run-NNN` — the run's **1-based run index**, zero-padded to 3 digits (`run-001`, `run-042`), so a run's ordinal position in the project's history is visible without opening it or comparing timestamps. The index is derived mechanically as **one past the highest `run-NNN__` index already present in the runs directory**; legacy and otherwise unindexed folders (created before this convention) are ignored when computing it rather than guessed at. An index past three digits keeps its full width rather than being truncated (`run-1000`). The prefix is generated by the naming utility (§5.5), never hand-formatted.
- `YYYY-MM-DD_HH-mm-ss` — the run's start time, keeping the timestamp ahead of the descriptive segments so folders still sort chronologically as plain strings within a single index sequence.
- `[Scope]` — one of the canonical Run Scopes (§5.2), never left as free text.
- `[Module-or-UserStory]` — the module, feature, or User Story/Bug ID the run targets (e.g. `FlightSearch`, `US-245_AddCabinClassFilter`), sanitized to a filesystem-safe form.

Examples:

```
run-001__2026-07-23_10-35-18__FullRun__FlightSearch
run-002__2026-07-23_11-02-41__Smoke__Login
run-003__2026-07-23_14-20-05__Regression__BookingFlow
run-004__2026-07-23_15-48-55__Targeted__US-245_AddCabinClassFilter
run-005__2026-07-23_16-10-32__Targeted__AgencyManagement
```

## 5.2 Canonical Run Scopes

Every folder name's Scope segment is exactly one of:

`FullRun` · `Regression` · `Smoke` · `Sanity` · `Targeted` · `Module` · `UserStory`

A run that only executed specific tests must read as `Targeted` (or another narrower scope) — it must never be named in a way that reads as a full/complete execution when it wasn't. Free-text scope/run-type input is normalized onto this set (e.g. `"Full Regression"` → `Regression`, `"Entire Project"` → `FullRun`, `"Custom"`/`"Bug"` → `Targeted`, `"Feature"` → `Module`, `"User Story"` → `UserStory`); anything unrecognized but non-empty also resolves to `Targeted` rather than silently defaulting to `FullRun`. Missing scope information resolves to `Unknown`.

## 5.3 Target Segment

The Module-or-UserStory segment is selected in this priority order: User Story ID/title → Module name → Feature name → free-text scope description. Missing/empty input resolves to `Unknown` rather than an empty segment.

## 5.4 Uniqueness, Duplicate Prevention, and Sanitization

1. Every segment is sanitized before the folder name is assembled: filesystem-unsafe characters are stripped, whitespace is collapsed, leading/trailing separators are trimmed, and the result is capped at 60 characters. An empty result after sanitization becomes `Unknown`.
2. Before creating the Run Workspace (§6), the Run Manager confirms the resulting folder name does not already exist under the project's runs directory. On collision, a deterministic `__2`, `__3`, … suffix is appended — never a randomized or silently overwritten name.
3. Because the folder name itself is index-ordered, time-ordered, and content-derived, no separate immutable Run ID is required for new runs; `run.json`'s own `folderName` field (§7) is the stable reference, and its `index` field (§7) restates the folder name's `run-NNN` ordinal. The index prefix itself is produced by the naming module's `formatRunIndex()`/`nextRunIndex()` helpers (§5.5), never assembled by hand.

## 5.5 The Naming Utility (single source of truth)

All of the above is implemented once, as code, at `platform_core/tools/run_manager/`:

- `runFolderName.js` — `generateRunFolderName(metadata, { existingNames, now, index, withIndex })` is the function every agent/skill/script must call to obtain a new run's folder name. By default it prefixes the name with `run-NNN__` (§5.1), taking the index one past the highest already present in `existingNames`; passing an explicit `index` pins it, and passing `{ withIndex: false }` omits the prefix entirely (used only by legacy migration, §5.6). It also exports `formatRunIndex(index)` (formats a 1-based index as the `run-NNN` prefix segment), `nextRunIndex(existingNames)` (computes the next index, ignoring unindexed/legacy folders), `parseRunFolderName()` (recognizes this convention with or without the index prefix — returning an `index` field when one is present — and the legacy `RUN-YYYYMMDD-XXX[-slug]` form), `normalizeScope()`, and `sanitizeSegment()`.
- `cli.js` — a thin CLI wrapper (`node platform_core/tools/run_manager/cli.js --scope <Scope> --target <Target> --started <ISO time>`) for agents/humans that aren't calling the module directly from JS. It also accepts `--index <N>` to pin the run index explicitly and `--no-index` to omit the `run-NNN__` prefix.
- `runFolderIndex.js` / `migrate.js` — the Legacy Run Folder Compatibility layer (§5.6).

No agent, skill, or script may hand-format a run folder name inline — doing so is exactly the duplicated-string-formatting problem this module exists to eliminate. See `platform_core/tools/run_manager/__tests__/` for the behavioral test suite covering sanitization, scope normalization, collision handling, and parsing.

## 5.6 Legacy Run Folder Compatibility Index

Every run folder that existed before this revision keeps its original `RUN-YYYYMMDD-XXX[-slug]` name and content **exactly as-is** — none are renamed by this revision. This is not a blanket policy exception; it is the outcome of a real, general safety check (`runFolderIndex.js`'s `isRenameSafe()`), which physically renames a legacy folder (via `git mv`, never copy+delete) only when zero other files in the project reference that folder's name. Applying that check to every run folder that exists as of this revision found real, live references (cross-run path dependencies where one run's automation package was extended in place by a later run, generated code paths, and manifest/history-table citations) — so every one of them stays on its legacy name, and is represented instead in a per-project compatibility index:

```
platform_core_data/runs/.run_folder_index.json   (or platform_core_data/runs/.run_folder_index.json)
```

Each entry records `{ legacyName, inferredNewName, confidence, source }` — `source` names exactly which document the Scope/Target were inferred from (`metadata/run.json`, that project's `run_configuration.md` history table, or its `*_RunManifest.md`), and `confidence` is `low` whenever no metadata could be found at all (in which case `inferredNewName` uses `Unknown` segments rather than a guess). `runFolderIndex.js`'s `resolveRunFolder(runsDir, identifier)` looks up either a legacy Run ID/folder name or a new-convention name and returns the real on-disk folder — this is what keeps history lookups, dashboards, and manifests working under either naming style without rewriting any of them.

Running the migration (`node platform_core/tools/run_manager/migrate.js --project <Name>`) is non-destructive (dry-run by default; writes only the index file), idempotent (re-running produces an unchanged index for folders already indexed), and reversible (an `--apply`-driven rename, on the rare folder that passes the safety check, is a plain `git mv` and trivially reverted). Backward compatibility takes priority over forcing a rename — a folder never gets renamed just because it would be convenient.

# 6. Workspace Structure

**Revision note (updated 2026-07-25 single-project restructure, revised 2026-07-27):** the project is fully self-contained under `platform_core_data/`, with no project-name path segment. The 2026-07-25 revision described Project Artifacts (a current-approved state under `platform_core_data/workspace/`) and Run Artifacts as **two siblings** under that root; that is no longer true. `pipeline.md` §7 removed `platform_core_data/workspace/` on 2026-07-27, so **`platform_core_data/runs/{{RUN_FOLDER}}/` is the one and only location a stage artifact lives** — there is no second, "current approved" tree for the Run Folder to mirror, and a stage writes its artifact exactly once, in its own run. This section also consolidates the previous cross-cutting `evidence/`, `screenshots/`, `videos/`, `logs/`, `network/` folders into the owning stage's own folder (`discovery/` for Explorer-produced evidence, `execution/` for Execution-produced evidence) rather than keeping them as separate top-level run folders — no evidence type is dropped, only regrouped by which stage produces it.

**On-demand folder creation (revised):** the Run Manager creates only `metadata/` before any Agent starts — every run has one, regardless of which stages it reaches. Every other subfolder is created **only at the moment the corresponding Agent actually produces its first output**, never upfront as an empty placeholder:

```
platform_core_data/
  runs/
    {{RUN_FOLDER}}/          <- e.g. run-001__2026-07-23_10-35-18__FullRun__FlightSearch (§5)
      metadata/              <- always created immediately
      context/               <- created only when Stage 1 writes to it
      discovery/             <- created only when Stage 2 writes to it
        findings/            <- created only when a Finding is actually raised
      test_design/           <- created only when Stage 3 writes to it
      manual_execution/      <- created only when Stage 4 writes to it
      automation/            <- created only when Stage 5 writes to it
      execution/             <- created only when Stage 6 writes to it
      reporting/             <- created only when Stage 7 writes to it
```

**Naming note:** every reference to a run's workspace path elsewhere in this document uses the placeholder `{{RUN_FOLDER}}` for brevity. For a run created under this document's current naming convention, that placeholder resolves to the full `run-NNN__YYYY-MM-DD_HH-mm-ss__Scope__Target` folder name (§5); for a pre-existing run, it resolves to that run's original `RUN-YYYYMMDD-XXX[-slug]` folder name, which is never renamed (§5.6).

A run that only ever reaches Stage 2 (Explorer) has exactly `metadata/` and `discovery/` on disk — `context/`, `test_design/`, `manual_execution/`, `automation/`, `execution/`, and `reporting/` are never created for that run. This applies for the life of the run: if it's later resumed and reaches further stages, each newly-reached stage's folder is created at that point, not before.

- `metadata/` — `run.json` (§7), `run_summary.md` (§9), and the Run Manifest (`RunManifest.md`, `pipeline.md` §7 — the per-stage record of timestamp, checkpoint status, approving reviewer, revision count, and Invocation Path), plus any other run-bookkeeping file. The one folder every run has, always.
- `context/` — the Project Context this run used (`ProjectContext.md`), edited in place per `pipeline.md` §7 — one file, no version suffixes.
- `discovery/` — Explorer Agent discovery snapshots, QA Assessment Report, and evidence (screenshots/videos/logs/network captures) produced during this run.
- `discovery/findings/` — Explorer Agent Finding evidence packages produced during this run (see `.claude/skills/explorer-skill/SKILL.md` §5.11).
- `test_design/` — Test Design Agent's Manual Test Suite, Traceability Matrix, and Coverage Report for this run.
- `manual_execution/` — Manual Execution Agent's Manual Execution Results, Manual Execution Summary, Automation Candidate Package, and captured evidence (screenshots, videos, notes, logs) for this run.
- `automation/` — Automation Agent's Automation Package, Plan, Manifest, Decision Report, Coverage Report, Suite Manifest, and Summary for this run. Per the Automation Asset Lifecycle (`pipeline.md` §12, added 2026-07-24), the Automation Package here is a **temporary working copy** of the project's Workspace Automation Baseline, not the authoritative copy — once it clears Automation Approval and is merged back into that baseline, its source code is removed from this folder (Cleanup, `pipeline.md` §12.5), leaving a permanent `automation_promotion.md` (Promotion Status, Merge Date, Approved By, Source Run, Workspace Destination, file-level Added/Modified/Deleted/Renamed/Discarded-Untracked lists, Conflicts, Merge Result, Notes) alongside the unaffected Plan/Manifest/Decision Report/Coverage Report/Suite Manifest/Summary.
- `execution/` — Automation Execution Agent's Execution Results and captured evidence (screenshots, traces, logs, HAR, framework reports) for this run.
- `reporting/` — Reporting Agent's Final QA Report for this run.

**Retroactive note (2026-07-17):** this replaces an earlier version of this section that had the Run Manager create the full seven-folder skeleton upfront, before any Agent ran. Existing runs created under that earlier behavior had empty subfolders for stages they never reached; those empty folders have been removed from NDC's existing runs to match this corrected behavior (no run content was touched — only folders with zero files were removed). The skeleton now has eight possible subfolders (`manual_execution/` added alongside `context/`, `discovery/`, `test_design/`, `automation/`, `execution/`, `reporting/`, and the always-present `metadata/`), created on the same on-demand basis.

This Run Workspace is **the sole location** for every artifact the pipeline produces — not an additive, run-scoped view of a separate current-approved tree. `platform_core_data/workspace/` was removed on 2026-07-27 (`workflows_and_pipelines/pipeline/pipeline.md` §7), and every stage now writes directly into its own run folder: the Project Context at `platform_core_data/runs/{{RUN_FOLDER}}/context/ProjectContext.md`, Discovery Artifacts at `platform_core_data/runs/{{RUN_FOLDER}}/discovery/*.md`, and so on for every stage in §6's structure. There is no second, authoritative "current approved" copy anywhere — approval flips the `status:` field in the artifact's own header and is recorded in the Run Manifest (`metadata/RunManifest.md`), per `pipeline.md` §7. The Run Manager still organizes and monitors that run-scoped view for history and archival; it is now organizing the artifacts themselves rather than a mirror of them.

# 7. Run Metadata

The Run Manager generates and maintains a single metadata file per run:

```
platform_core_data/runs/{{RUN_FOLDER}}/metadata/run.json
```

**Schema revision (2026-07-23, `index` added 2026-07-27):** `run.json` for runs created under §5's current naming convention uses the schema below — `folderName`, `index`, `scope`, and `target` replace the retired `runId`/`displayName` fields (the folder name itself is now the stable, self-descriptive reference; see §5.4 item 3). Title/Description/Objective/Workflow are unchanged from the 2026-07-21 revision. Pre-existing runs' `run.json` files keep their original field names and shape unchanged; they are not migrated to this schema (§5.6).

`run.json` must contain the following fields. There is deliberately no `project` key (removed 2026-07-25): the platform hosts one project, so recording which one a run belonged to would be a constant, and a constant that looks like a selector invites code to branch on it. Existing run folders that still carry the key are left as-is — they are immutable run history (§5.6).

| JSON key | Description |
|---|---|
| `folderName` | This run's full folder name, per §5.1 (e.g. `run-001__2026-07-23_10-35-18__FullRun__FlightSearch`) — generated via `platform_core/tools/run_manager` (§5.5), never hand-formatted |
| `index` | This run's 1-based ordinal, per §5.1 (e.g. `1`, `42`) — identical to the folder name's `run-NNN` segment, and derived from it by the same naming module (`formatRunIndex()`/`nextRunIndex()`, §5.5). Absent for legacy/unindexed runs, which are never renamed (§5.6) |
| `scope` | This run's canonical Run Scope, per §5.2 (e.g. `"FullRun"`, `"Targeted"`) — identical to the folder name's Scope segment |
| `target` | The Module/UserStory/Feature this run targets, per §5.3 (e.g. `"FlightSearch"`) — identical to the folder name's Target segment before sanitization |
| `title` | A short, human-readable title generated from the same Scope/Target context (e.g. `"Full Run - Flight Search Validation"`) |
| `description` | A one-paragraph, human-readable description of what this run does and why, generated from the same context |
| `objective` | A one-sentence statement of this run's specific validation objective |
| `workflow` | The workflow this run executes, if invoked via a named workflow in `workflows_and_pipelines/workflows/` (e.g. `first_run`, `user_story_run`, `bug_fix_run`); `unversioned` if run ad hoc, outside any named workflow |
| `pipelineVersion` | The version identifier of `workflows_and_pipelines/pipeline/pipeline.md` in effect for this run |
| `projectContextVersion` | The revision count of the Project Context artifact this run used (how many times it has been edited in place), per `workflows_and_pipelines/pipeline/pipeline.md` §7 — version suffixes were retired on 2026-07-27, so this is a count, not a `v1`-style suffix |
| `explorerVersion` | The version identifier of `.claude/skills/explorer-skill/SKILL.md` in effect for this run |
| `testDesignVersion` | The version identifier of `.claude/skills/test-design-skill/SKILL.md` in effect for this run |
| `manualExecutionVersion` | The version identifier of `.claude/skills/manual-execution-skill/SKILL.md` in effect for this run |
| `automationVersion` | The version identifier of `.claude/skills/automation-skill/SKILL.md` in effect for this run |
| `executionVersion` | The version identifier of `.claude/skills/automation-execution-skill/SKILL.md` in effect for this run |
| `reportingVersion` | The version identifier of `.claude/skills/reporting-skill/SKILL.md` in effect for this run |
| `browser` | The browser (name/version) used for browser-driven stages of this run |
| `environment` | The target environment, per the Project Context's Environment Constraints |
| `resolution` | The viewport/screen resolution used for browser-driven stages |
| `createdBy` | Who/what initiated the run — the requesting human's identifier if known, else `"Run Manager"` |
| `startedTime` | Timestamp the run entered `Preparing` |
| `finishedTime` | Timestamp the run reached a terminal status (`Completed`, `Failed`, or `Cancelled`); absent while the run is still active |
| `duration` | `finishedTime − startedTime`; absent while the run is still active |
| `status` | The run's current value from the Execution Status enum (§8) |

Notes:
- A "version identifier" for a component that does not yet carry an explicit version tag is recorded as `unversioned` rather than invented — the Run Manager records what exists, it does not assign version numbers to specs that don't declare one.
- `title`, `description`, and `objective` are generated once, at run creation, from the same Scope/Target context as `folderName` (§5.3) — they are not re-derived or altered by later stages.
- `run.json` is updated in place as the run progresses (e.g., `status` changes, `finishedTime`/`duration` are populated on completion) — this is metadata *about* the run, not a project artifact whose content the Run Manager is forbidden from touching (§10).

# 8. Execution Status

Every run's status is exactly one of the following values at any given time:

| Status | Meaning |
|---|---|
| **Preparing** | The Run Manager has generated the run's folder name (§5) and is creating the Run Workspace and initial `run.json`; no Agent has started yet. |
| **Running** | At least one Agent stage is actively executing for this run. |
| **Paused** | Execution has been deliberately suspended (not a checkpoint — a manual pause) and is expected to resume. |
| **Waiting For Approval** | The run is stopped at one of the Human Review / Automation Approval checkpoints defined in `workflows_and_pipelines/pipeline/pipeline.md` §5, awaiting a reviewer decision. |
| **Completed** | The run reached the terminal Reporting Agent stage and finished successfully. |
| **Failed** | The run stopped due to an error condition (e.g., an Agent could not complete its stage) rather than a deliberate pause or rejection. |
| **Cancelled** | The run was deliberately terminated before reaching a terminal stage, by explicit human decision. |

The Run Manager transitions a run's status based on mechanical signals (an Agent stage starting/finishing, a checkpoint opening per `workflows_and_pipelines/pipeline/pipeline.md` §5.3, an error being raised, an explicit pause/cancel instruction) — never based on its own interpretation of whether the Agents' output is good or correct.

# 9. Run Summary

Once a run reaches a terminal status (`Completed`, `Failed`, or `Cancelled`), the Run Manager publishes:

```
platform_core_data/runs/{{RUN_FOLDER}}/metadata/run_summary.md
```

**Header revision (2026-07-21, fields updated 2026-07-23):** for runs created under §5's current naming convention, `run_summary.md` opens with a `# Run Summary` heading followed by the run's descriptive identity fields (sourced verbatim from `run.json`, §7), before the pre-existing factual roll-up. Pre-existing runs' `run_summary.md` files are unchanged (§5.6).

`run_summary.md` must begin with:

```markdown
# Run Summary

- Folder Name: {folderName}
- Workflow: {workflow}
- Project: {project}
- Run Scope: {scope}
- Target: {target}
- Execution Purpose: {objective}
- Description: {description}
- Status: {status}
- Duration: {duration}
```

...then continue with the existing summary:

| Field | Description |
|---|---|
| Visited Screens | Count of distinct screens/states captured in this run's `discovery/` (a mechanical count of Explorer Agent discovery snapshots, not a judgment of exploration completeness) |
| Executed Agents | Which of the seven Agents ran during this run, and in what order |
| Generated Artifacts | A count/list of artifacts produced across all Run Workspace subdirectories (§6) |
| Findings Count | Count of Finding evidence packages under this run's `discovery/findings/` |
| Evidence Count | Count of evidence items across `discovery/` (screenshots/videos/logs/network captures) and `execution/` (screenshots/traces/logs/HAR/framework reports) |
| Screenshots Count | Count of screenshot files under `discovery/` and `execution/` (including any embedded within `discovery/findings/` evidence packages) |
| Videos Count | Count of video recordings under `discovery/` and `execution/` (including any embedded within `discovery/findings/` evidence packages) |
| Logs Count | Count of log files under `discovery/` and `execution/` |
| Coverage | The mechanical ratio of in-scope modules/screens actually visited (per Discovery Artifacts) against the Project Context's declared in-scope list — a count, not an assessment of whether that coverage was sufficient |
| Overall Status | The run's final value from the Execution Status enum (§8) — the same value as the opening block's `Status`, repeated here as it was in the pre-existing summary shape |

`run_summary.md` is a factual roll-up of counts and statuses drawn from what each Agent already produced, plus the descriptive identity fields already generated for `run.json` — it must never include an assessment of quality, correctness, or defect severity. Any such judgment belongs in the Explorer Agent's Findings Summary or the Reporting Agent's Final QA Report, not here.

# 10. Rules

1. The Run Manager never performs testing of any kind — it does not drive a browser, does not call an application, and does not execute test cases.
2. The Run Manager never interprets results — it counts and records what Agents produced; it does not decide whether those results are correct, acceptable, or a defect.
3. The Run Manager never changes the content of any project artifact produced by an Agent. It may organize where artifacts live within the Run Workspace (§6) and it may create/update its own metadata files (`run.json`, `run_summary.md`), but it must never edit, rewrite, or delete an Agent-produced artifact.
4. The Run Manager only prepares and coordinates execution — folder-name generation (§5, via `platform_core/tools/run_manager`), Title/Description generation (§7), workspace creation, metadata tracking, status tracking, and summary publication are its entire mandate.
5. The Run Manager must not bypass, shortcut, or auto-resolve any Human Review or Automation Approval checkpoint defined in `workflows_and_pipelines/pipeline/pipeline.md` §5 — reaching `Waiting For Approval` status is as far as it goes; only a human decision moves the run past that point.
6. The Run Manager must not read the PRD — per `workflows_and_pipelines/pipeline/pipeline.md` §6 Rule 4, only Stage 1 (Project Context Agent) is permitted to do so, and the Run Manager is not a stage.

# 11. Inputs & Outputs

| | |
|---|---|
| **Inputs** | Project Name · Run Configuration (target environment, browser, resolution) · signals from each Agent stage marking start/completion/error · checkpoint state from `workflows_and_pipelines/pipeline/pipeline.md` §5.3 |
| **Outputs** | Run Workspace (§6) · `run.json` (§7) · `run_summary.md` (§9) |

The Run Manager does not consume the PRD, the Project Context's business content, or any Agent's analytical output as *input to a decision* — it only observes that those artifacts exist, where they are, and what stage produced them.

# 12. Allowed Operations

- File system: create directories (Run Workspace), create/update the Run Manager's own metadata files (`run.json`, `run_summary.md`), read (not write) Agent-produced artifacts strictly to count/organize them.
- Read-only directory-listing and file-counting operations for compiling the Run Summary (§9).

**Not permitted:** browser automation tools, any tool that edits or deletes an Agent-produced artifact's content, any tool that mutates application data, and any tool that would let it act as an Agent (e.g., generating a Finding, test case, or report section).

# 13. Architecture

The Run Manager sits outside the 7-stage Agent pipeline defined in `workflows_and_pipelines/pipeline/pipeline.md`. It is the concrete specification of the "Pipeline Orchestrator (tooling, not a person)" role already named in that document's §5.3 and §9 Roles Summary.

```
                    ┌─────────────────────────────────────────┐
                    │              Run Manager                 │
                    │  (orchestration component, not an Agent) │
                    │                                           │
                    │  Generates run folder name (§5),          │
                    │  Run Workspace, run.json                  │
                    │  Tracks status through the run            │
                    │  Publishes run_summary.md at the end      │
                    └───────────────────┬───────────────────────┘
                                         │ provides workspace paths to
                                         ▼
   Stage 1        Stage 2        Stage 3        Stage 4        Stage 5        Stage 6        Stage 7
Project Context → Explorer  → Test Design → Manual     → Automation → Automation → Reporting
   Agent            Agent        Agent      Execution      Agent      Execution     Agent
                                             Agent                      Agent
```

It orchestrates *execution* — allocating identity, workspace, and tracking to a run — but it is not considered an Agent, does not appear in the Pipeline Overview diagram in `workflows_and_pipelines/pipeline/pipeline.md` §3, and does not change that diagram's stage order, gates, or artifact contracts.
